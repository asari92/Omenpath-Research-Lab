# Блоковый режим разработки до сдачи

## Цель

Ускорить завершение Omenpath Research Lab без отказа от Final Spec, TDD,
traceability и обязательной проверки. Оставшиеся стадии выполняются тремя
блоками с одной пользовательской сверкой после каждого блока, а не после
каждой стадии.

## Единица планирования

Для каждого блока создаётся один подробный execution-plan:

- Block C: Stages 9–14;
- Block D: Stages 15–21;
- Block E: Stages 22–27.

План содержит отдельные разделы, scope и DoD для каждой стадии. Границы стадий
сохраняются: реализация более поздней стадии не должна незаметно попадать в
коммиты более ранней.

## Исполнение внутри блока

После утверждения block plan агент может последовательно пройти все стадии
этого блока без ожидания дополнительного подтверждения пользователя.

Для каждого meaningful checkpoint сохраняется:

```text
requirements → tests → RED → minimal implementation → focused GREEN
```

Для каждой стадии сохраняются отдельные RED/GREEN-коммиты, полный обычный test
suite и актуализация traceability/worklog. Race detector, vet, build и полный
suite обязательно повторяются на границе всего блока. Если проверка быстрая,
её разрешено запускать чаще.

Тесты и production-работа могут исследоваться параллельно только для
независимых задач. Параллельные агенты используют изолированные worktrees;
интеграция выполняется последовательно после review, чтобы не смешивать
границы стадий и не терять RED/GREEN evidence.

## Stop conditions

Работа немедленно останавливается внутри блока только при:

- настоящем противоречии с `00_FINAL_SPEC_v5.md`;
- отсутствующей product semantics, которую нельзя вывести из Final Spec;
- необходимости внешних credentials или необратимого внешнего действия;
- неустранённом падении обязательной проверки.

Обычные технические ошибки, failing tests и локальные integration defects не
требуют пользовательского подтверждения: они диагностируются и исправляются
внутри текущего блока.

После завершения блока агент обязан остановиться, дать русскоязычный отчёт и
«сверить часы» с пользователем. Следующий блок без этого не начинается.

## Проверка блока

На границе каждого блока выполняются:

```bash
gofmt -l .
go vet ./...
go build ./...
go test -count=1 ./...
go test -race -count=1 ./...
```

Дополнительно проверяются Final Spec, requirements, traceability, worklog,
scope текущего блока, чистота Git и отсутствие реализации следующего блока.

## Известные будущие гейты

- Recommendation gate закрыт до реализации Block C: пользователь утвердил
  deterministic decision table, зафиксированную в Final Spec §23.1 и
  `docs/superpowers/specs/2026-09-04-recommendation-engine-design.md`. Backend
  реализуется в Stage 12, rendering — в Stage 17.
- Для Stage 25 могут понадобиться deployment credentials или выбор платформы.
  Этот вопрос поднимается на сверке после Block D, если ранее не решён.

## Приоритет при дефиците времени

Приоритет остаётся сквозным и проверяемым:

```text
domain/events → persistence → manager → REST/WS → основной frontend
→ deployment → расширенная QA и полировка
```

Scope из Final Spec не удаляется. Если дедлайн делает полный объём
недостижимым, агент сообщает это на ближайшей блоковой сверке и предлагает
явный cut, а не молча пропускает требования.
